# Durable family follow-ups

Apply `supabase/outreach-followups.sql` after `outreach-requests.sql`. This ledger records a family's report of a callback promise or next action. It never places a call, sends a message, or changes an outreach request or booking status. Completing a task records that the family marked it done; it is not office confirmation.

`GET /api/outreach-followups` returns `{followups, serverNow}` for the authenticated owner only, open first and earliest due first, capped at 100. Optional `?requestId=UUID` scopes the list. Each item has `followupId, requestId, kind, assignee, note, dueAt, source, channel, status, createdAt, completedAt`. Due timestamps are UTC; render using the family's browser timezone. Compare open items against `serverNow` for overdue state. Load once on account entry/return and after mutations; do not poll each request. The 100-row cap is a bounded initial surface, not a complete export.

`POST /api/outreach-followups` accepts exactly `{followupId, requestId, kind, assignee, note, dueAt?, source, channel}`. IDs are UUIDs generated once per action; retry with the same ID and details. `kind` is `promised_callback | next_action`, `assignee` is `office | family | coordinator`, note is a short summary (1–500 characters), and channel is `phone | email | other`. Do not paste transcripts. `source` must be `user_reported`. Legacy phone/email reports use that same attribution. Due time requires seconds and explicit `Z` or an offset, e.g. `2026-11-18T09:00:00-05:00`; omit when unknown. Convert datetime-local input in the browser to ISO before submitting.

`PATCH /api/outreach-followups` accepts exactly `{followupId}` and marks an owned item done. Replays do not append duplicate history. A new POST returns 201, replay/complete 200, conflicting POST reuse 409, unknown owned request/followup 404. Both writes require same-origin JSON and are limited to 4KB. The route verifies the account with `getUser()` and calls RPCs on that same authenticated user client. No server-only key is needed. RPCs take no owner parameter: they derive `auth.uid()` internally and reject missing or anonymous accounts.

Tables enforce owner-scoped reads via RLS; browser roles cannot mutate either table. Authenticated caller-owned definer functions atomically append immutable recorded/completed events. Execution is revoked from public, anon, and service_role; direct table mutation remains revoked. The SQL checks the authenticated user exists and is not an anonymous Supabase account. `validated_service` is reserved in storage for a future authenticated evidence adapter; no current RPC accepts that attribution. No upload or outbound provider integration is introduced.
